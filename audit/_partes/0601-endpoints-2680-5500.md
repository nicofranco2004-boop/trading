## Endpoints (main.py 2680–5500)

Este tramo cubre **identidad y cuenta** (registro, login, verificación de email, reset de contraseña, cierre de cuenta, "empezar de cero", perfil de inversor), **brokers**, **config de tipos de cambio**, **cotizaciones del dólar**, **snapshots diarios de cartera** y **la serie histórica de FX**. Son 25 endpoints. El último `@app.` del rango está en `backend/main.py:5170`; de ahí a 5500 hay solo helpers (los fetchers de benchmarks), que van en la última subsección.

### Cómo se autentica todo este tramo (contexto necesario para leer lo de abajo)

[V] Tres dependencias distintas, definidas justo antes del rango:

| Depends | Línea | Qué hace |
|---|---|---|
| `get_current_user` | `backend/main.py:2692` | Lee el JWT de la cookie HttpOnly `rendi_token`; si no hay, cae al header `Authorization: Bearer`. Valida firma, que el user exista y que el claim `pca` coincida con `users.password_changed_at` (así un cambio de contraseña invalida los tokens viejos). |
| `get_admin_user` | `backend/main.py:2721` | `get_current_user` + `users.is_admin`. **No se usa en ningún endpoint de este tramo.** |
| `get_effective_user` | `backend/main.py:2806` | `get_current_user` + contexto de cliente del Plan Asesor: si viene el header `X-Rendi-Client-Id` y el vínculo existe en `advisor_clients` con `status='active'`, **devuelve el uid del CLIENTE**, no el del asesor. Es el `Depends` de los 22 endpoints autenticados de este tramo. |

[V] `_resolve_client_context` (`backend/main.py:2767`) tiene una lista de **prefijos exentos** (`CLIENT_CTX_EXEMPT_PREFIXES`, `backend/main.py:2749-2758`): `/api/auth`, `/api/billing`, `/api/admin`, `/api/advisor`, `/api/me`, `/api/push`, `/api/plan/track`, `/api/feedback`. En esos prefijos el header **se ignora** y `get_effective_user` devuelve el uid real.

**Consecuencia práctica de este tramo** [V]: los 9 endpoints bajo `/api/auth/*` y los 3 bajo `/api/me*` usan `Depends(get_effective_user)` pero, por estar en prefijo exento, se comportan **idénticamente a `get_current_user`**. Los que SÍ heredan el contexto de cliente son: `/api/brokers` (4), `/api/config` (2), `/api/dolar`, `/api/snapshots` (2) y `/api/fx-rates`.

[V] El comentario del propio código lo marca como **fail-open** (`backend/main.py:2764-2766`): "todo endpoint futuro FUERA de estos prefijos hereda el contexto de cliente".

[V] Rate limiting: `_check_rate_limit` (`backend/main.py:395`) es **in-memory por proceso** (`_rate_store`, `backend/main.py:309`) y la clave es **siempre** `f"{ip}|{suffix}"` (`backend/main.py:397`). Ver la rareza que esto genera en `/api/auth/login`.

### `POST /api/auth/register` — `backend/main.py:3094`

- **Qué hace**: crea la cuenta. Si el email es el del admin (hash constante, `_is_admin_email`, `backend/main.py:131`), se auto-verifica y devuelve token; cualquier otro email queda con `email_verified=0`, recibe un código OTP de 6 dígitos por mail y NO recibe token.
- **Quién puede llamarlo**: **SIN AUTENTICACIÓN** (público). Gates propios: `ALLOW_REGISTRATION` (`backend/main.py:121`, env `ALLOW_REGISTRATION`) — si está en false solo pasa el signup del admin (`backend/main.py:3099-3101`); y rate limit 5 llamadas / 5 min por IP (`backend/main.py:3102`).
- **Params**: body `RegisterIn` (`backend/main.py:2861`) — `email` (≤254, validado contra `_EMAIL_RE`, normalizado a lower+strip), `password` (10–128), `name` (opcional, ≤100). Inyecta `Request`, `Response` y `BackgroundTasks`.
- **Tablas**: escribe `users`, `config` (`tc_mep`/`tc_blue` = 1415), `email_verification_codes` (vía `_create_verification_code`). Solo en el path admin: `UPDATE positions|monthly_entries|operations|config SET user_id=? WHERE user_id=0` e `INSERT OR IGNORE INTO brokers` (`backend/main.py:3120-3143`).
- **Servicios externos**: Resend, vía `billing.emails.send_verification_code`, pero **en un BackgroundTask** (`backend/main.py:3159-3161`) — el request no espera al mail.
- **Devuelve**: no-admin → `{needs_verification: true, email, message}`. Admin → `{token, name, is_admin: true}` + cookie. Email duplicado → 409 con `detail = {code: "EMAIL_ALREADY_REGISTERED", error, email}`.
- **Efectos secundarios**: BackgroundTask de email; `set_auth_cookie` solo en el path admin; decorado con `@reintentar_si_trabada` (`backend/main.py:3095`) → reintenta el handler entero ante `database is locked`.
- **Rarezas**:
  - [V] La "absorción de datos legacy `user_id=0`" (`backend/main.py:3121-3143`) sigue viva y solo el admin la dispara. Infiere `currency` del broker por nombre contra `ARS_BROKER_NAMES` / `CRYPTO_BROKER_NAMES` (`backend/main.py:2835`, `2842`). En ese set aparece `'pppi'` — [I] muy probablemente un typo de `ppi`, el broker que sí tiene parser (`backend/importing/parsers/`), con lo cual PPI se infiere USD en vez de ARS.
  - [V] `backend/main.py:3145-3146` usa `INSERT OR IGNORE INTO config VALUES ('tc_mep','1415',?)` — **VALUES posicional**, exactamente el patrón contra el que advierte el comentario de `PUT /api/config` (`backend/main.py:4578-4580`: "el VALUES posicional de antes asumía el orden … la próxima columna que se agregue lo rompe en silencio"). Dos criterios distintos para la misma tabla, en el mismo archivo.
  - [V] El check `ALLOW_REGISTRATION` corre **antes** del rate limit: con registro cerrado, un atacante puede enumerar/pegarle sin gastar cupo.
  - [I] `@reintentar_si_trabada` sobre un handler que hace `background_tasks.add_task`: si el lock aparece *después* del `add_task`, el reintento agregaría una segunda tarea de email. El propio docstring del decorador advierte sobre efectos externos no idempotentes (`backend/main.py:539-541`). No verifiqué que sea alcanzable — el `add_task` está después del `commit`.
  - [V] `approved` se fuerza a 1 siempre; la columna sobrevive por compat de esquema (comentario en `backend/main.py:3106-3109`).

### `POST /api/auth/login` — `backend/main.py:3187`

- **Qué hace**: valida credenciales, exige email verificado, emite JWT + cookie, registra el login y avisa por mail si el dispositivo es nuevo.
- **Quién puede llamarlo**: **SIN AUTENTICACIÓN** (público). Dos rate limits: 10/60s por IP y 10/60s por `login_email:<email>` (`backend/main.py:3191-3192`).
- **Params**: body `LoginIn` (`backend/main.py:2882`) — `email` (≤254), `password` (≤128). No hay validación de formato de email acá (a diferencia de `RegisterIn`).
- **Tablas**: lee `users` (`SELECT *`); escribe `users.last_login_at` y `login_history` (vía `_record_login_and_maybe_alert`).
- **Servicios externos**: Resend (`billing.emails.send_new_login_alert`) — **sincrónico dentro del request**, envuelto en try/except.
- **Devuelve**: `{token, name, is_admin}` + cookie `rendi_token`. 401 "Credenciales inválidas"; 403 con `{code: "EMAIL_NOT_VERIFIED", error, email}` si falta verificar.
- **Efectos secundarios**: cookie; INSERT en `login_history`; posible email de alerta de nuevo dispositivo.
- **Rarezas**:
  - [V] **El rate limit "por email" no es por email**. El comentario dice "mitiga brute-force distribuido sobre una cuenta puntual" (`backend/main.py:3189`), pero `_check_rate_limit` arma la clave como `f"{ip}|{suffix}"` (`backend/main.py:397`): el limitador de email **también está scopeado por IP**. Un ataque distribuido sobre una sola cuenta no se frena. Lo mismo aplica a `forgot-password` y `verify-email`.
  - [V] El rate store es per-process (`backend/main.py:307`, "Para multi-worker o multi-host conviene migrar a Redis") → con más de un worker los límites se multiplican por N.
  - [V] `pwd_ctx.dummy_verify()` cuando el user no existe (`backend/main.py:3196`) — bien, evita el side-channel de timing.
  - [V] El body sigue devolviendo `token` en claro "por back-compat" además de la cookie HttpOnly.
  - [V] No hay `@reintentar_si_trabada` acá pese a que el handler escribe (`last_login_at` + `login_history`).

### `POST /api/auth/verify-email` — `backend/main.py:3240`

- **Qué hace**: confirma el email con el OTP de 6 dígitos, marca `email_verified=1` y **loguea al user** (emite token + cookie). Es el signup "real".
- **Quién puede llamarlo**: **SIN AUTENTICACIÓN**. Rate limit 5/60s por `verify_email:<email>` (+IP).
- **Params**: body `VerifyEmailIn` (`backend/main.py:2892`) — `email` (≤254), `code` (exactamente 6 dígitos, `pattern=r"^\d{6}$"`).
- **Tablas**: lee `users`, `email_verification_codes`; escribe `email_verification_codes.used_at`, `users.email_verified`, `login_history`. Además hace `SELECT COUNT(*) FROM users WHERE email_verified=1 AND is_admin=0` (contador global, `backend/main.py:3311-3313`).
- **Servicios externos**: Resend ×2 — `send_welcome_free` al usuario y `send_new_signup_admin` a `ADMIN_NOTIFY_EMAIL` (`backend/main.py:2920`, env `ADMIN_NOTIFY_EMAIL`), este último solo mientras el contador global de signups ≤ `ADMIN_SIGNUP_ALERT_LIMIT` (`backend/main.py:2921`, env, default 100). Ambos sincrónicos dentro del request.
- **Devuelve**: `{token, name, verified: true}` + cookie. Errores: 400 genérico "Código inválido o expirado" (no leakea si el email existe) y 400 "Tu cuenta ya está verificada."
- **Efectos secundarios**: cookie; `login_history`; 2 emails.
- **Rarezas**:
  - [V] `hmac.compare_digest` para comparar el código (`backend/main.py:3273`) — bien.
  - [V] Solo se prueba **el código más reciente** no usado (`ORDER BY created_at DESC LIMIT 1`), y `_create_verification_code` ya invalida los previos.
  - [V] **`try:` … `except HTTPException: raise` (`backend/main.py:3330-3331`) es un no-op**: envuelve todo el cuerpo para re-lanzar exactamente lo que ya se lanzaría. Código muerto.
  - [V] El mensaje "Tu cuenta ya está verificada. Iniciá sesión." **sí** leakea que ese email existe y está verificado — contradice el comentario de dos líneas antes ("Mensaje genérico para no leakear si el email existe", `backend/main.py:3258`).
  - [V] `POST /api/auth/verify-email` es efectivamente un **login sin contraseña** para toda cuenta no verificada: quien adivine el OTP de 6 dígitos entra. El rate limit es 5/min **por IP+email**, así que desde N IPs el espacio de 900.000 códigos se explora más rápido de lo que sugiere el comentario. [I] riesgo acotado por el TTL de 15 min (`EMAIL_CODE_TTL_MINUTES`, `backend/main.py:2912`).
  - [V] El envío del welcome + la alerta al admin son sincrónicos: dos round-trips a Resend adentro del request más frágil del funnel — justo lo que `register` evitó mandando el suyo a un BackgroundTask.
  - [V] `SELECT COUNT(*) FROM users` sin índice-friendly filter en cada verificación de email. Con la base actual es barato; escala linealmente.

### `POST /api/auth/resend-verification` — `backend/main.py:3334`

- **Qué hace**: genera un OTP nuevo y lo manda por mail. Idempotente y silencioso si el user no existe o ya está verificado.
- **Quién puede llamarlo**: **SIN AUTENTICACIÓN**. Rate limits: 1/60s y 5/hora, ambos por `<ip>|resend*:<email>`.
- **Params**: body `ResendVerificationIn` (`backend/main.py:2897`) — solo `email`.
- **Tablas**: lee `users`; escribe `email_verification_codes` (invalida previos + inserta).
- **Servicios externos**: Resend (`send_verification_code`), **sincrónico**.
- **Devuelve**: siempre `{sent: true, message}` (respuesta genérica).
- **Rarezas**:
  - [V] **La clave del rate limit no normaliza el email**: `suffix=f"resend:{data.email.lower()}"` (`backend/main.py:3340-3341`) usa `.lower()` **sin `.strip()`**, mientras la búsqueda en DB usa `email_norm = data.email.strip().lower()` (`backend/main.py:3342`).   - [V] `EMAIL_CODE_RESEND_COOLDOWN_SECONDS = 60` (`backend/main.py:2913`) está definida y **no la usa nadie** — el 60 está hardcodeado en la llamada. Constante muerta (verificado con grep sobre todo `backend/`).

- **Devuelve**: array ascendente `[{date, blue, mep}, …]`.
- **Rarezas**:
  - [V] Devuelve por default **10 años de filas diarias (~3650 objetos)** en una sola respuesta, sin paginación ni compresión declarada. El docstring dice que el frontend la fetchea una vez por sesión y la cachea en memoria.
  - [V] Igual que en snapshots, `days` es un `LIMIT` de filas, no una ventana de fechas.
  - [V] `mep` se lee con un guard raro: `r["mep_venta"] if "mep_venta" in r.keys() else None` — chequeo de existencia de columna hecho sobre el `Row` ya materializado (funciona, pero es un tercer patrón distinto para el mismo problema que `_tiene_columna` resuelve dos endpoints más arriba).
  - [V] Un endpoint que sirve **datos globales de mercado** exige auth, y además acepta (y descarta) el header de contexto de cliente.
